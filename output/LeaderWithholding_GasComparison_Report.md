# 가스 사용량 비교 보고서: 리더 보류 시나리오

## 개요

이 보고서는 CommitReveal2 프로토콜에서 리더 보류(Leader Withholding) 처리를 위한 두 가지 접근 방식의 가스 비용을 비교합니다:

1. **기존 방식 (`test_LeaderWithholdingGas`)**: 리더 선출 없이 직접 재개
   - 경로: `submitMerkleRoot() → failToRequestSOrGenerateRandomNumber() → resume() → submitMerkleRoot() → generateRandomNumber()`

2. **리더 선출 방식 (`test_LeaderWithholdingWithLeaderSelectionGas`)**: 커밋-공개 리더 선출 후 재개
   - 경로: `submitMerkleRoot() → failToRequestSOrGenerateRandomNumber() → commit() → reveal() → resume() → submitMerkleRoot() → generateRandomNumber()`

## 주요 관찰 사항

### 1. 확장성 특성
- **기존 방식**은 **운영자당 ~7,608 가스** 증가 (주로 `generateRandomNumber`에서 발생)
- **리더 선출 방식**은 **운영자당 ~54,559 가스** 증가 (~7.2배 높은 증가율)
- 차이의 대부분은 커밋과 공개 단계에서 발생

### 2. 기본 비용 차이
- 3 운영자 기준, 리더 선출은 **81,129 가스** 추가 (+21.7% 오버헤드)
- 32 운영자 기준, 리더 선출은 **1,490,451 가스** 추가 (+247.5% 오버헤드)

### 3. 트레이드오프 분석
| 측면 | 기존 방식 | 리더 선출 방식 |
|------|----------|----------------|
| **가스 효율성** | ✅ 낮은 가스 비용 | ❌ 높은 가스 비용 |
| **탈중앙화** | ❌ 중앙화된 리더 지정 | ✅ 탈중앙화된 리더 선출 |
| **공정성** | ❌ 미리 정해진 리더 | ✅ 커밋-공개를 통한 무작위 리더 |
| **공격 저항성** | ❌ 리더를 미리 알 수 있음 | ✅ 집단 무작위성으로 리더 결정 |

## 결론

**리더 선출 방식**은 상당한 가스 오버헤드(운영자 수에 따라 +21.7%에서 +247.5%)를 도입하며, 이는 주로 커밋-공개 메커니즘에 기인합니다. 그러나 이 오버헤드는 중요한 보안 이점을 제공합니다:

1. **예측 불가능성**: 공개 단계가 완료될 때까지 새 리더를 알 수 없음
2. **공정성**: 참여하는 모든 운영자가 동등한 선출 기회를 가짐
3. **담합 저항성**: 선출 과정에서 다수 운영자의 참여 필요

접근 방식의 선택은 구체적인 요구사항에 따라 달라집니다:
- **가스 민감 애플리케이션**: 기존 방식 사용
- **보안 중시 애플리케이션**: 리더 선출 방식 사용
